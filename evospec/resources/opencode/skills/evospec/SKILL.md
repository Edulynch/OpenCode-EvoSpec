# EvoSpec Protocol

## Natural-language recovery: read only

When the user asks "¿dónde seguimos?", "¿en qué quedamos?", "what were we doing?", or otherwise requests the current project context, activate this skill automatically. The user need not name EvoSpec or invoke a command. Call **only** `evospec_context` for the executing session's project/worktree. A question about status is not a request to initialize a project, accept an agreement again, plan, execute, advance a lifecycle, change permissions, or invoke `evospec_continuation`. Do not write to `.evospec` or any other file.

Answer briefly in ordinary language: current Feature and Slice titles, the known Task, the last reported checkpoint, and what remains or blocks continuation, **only where authoritative context supplies each fact**. `accepted_slice.checkpoint` is the *initial accepted checkpoint*, not evidence of work completed. If present, `task_progress.checkpoint` is a later report for the same Task: identify it as `REPORTED_UNVERIFIED`, not independently verified completion; when absent or null, state that no later Task progress is recorded. The separate `progress` and `outcome` fields may explain current work or a blocker, but neither proves a criterion passed. Do not invent acceptance criteria, agreements, Task status, or verification evidence missing from the returned context. Show technical IDs and revisions only when requested or needed to distinguish ambiguous work.

When no Task is active, inspect `work_queue` for accepted Slice details attached to parked items. List their available human titles and state as **inactive**; an accepted parked Task is not the current Task. If two or more valid items could resume, or the queue projection is incomplete, report the alternatives or limitation and ask only the clarification needed. Never select, reactivate, or modify a parked item from a status question. No agreement in the queue means no agreed Task title to invent.

If `evospec_context` is unavailable or its call fails, say that canonical state could not be verified and stop. Do not substitute Engram, other agent memories, past messages, an unrelated repository, or a guessed checkpoint for a native context result. If state is missing, invalid, from another worktree, or ambiguous, explain the uncertainty and stop without initialization, repair, search across unrelated worktrees, or a guessed resume point. Ask for a material clarification only when necessary. If the user later explicitly asks to perform work, begin the normal protocol below with fresh context and its legal actions; a read-only answer confers no execution authority.

## Explicit lifecycle work

Call `evospec_context` and `evospec_continuation` before repository inspection, tests, implementation state, or EvoSpec lifecycle mutation. Internal task, todo, and reasoning work may precede context only when it does not mutate the repository or EvoSpec and does not claim authorization. Treat returned `legal_actions`, preflight requirements, lifecycle, lock metadata, outcome, Autonomy Envelope, and revision as authority. Context chooses legality; never infer an allowed action from a phase name. Every mutation includes that exact `expected_revision`; reload canonical context after every Core mutation. On `STALE_REVISION`, discard conclusions tied to the old revision, refresh, and reevaluate the intended operation; replay only when current Core legality and the exact offered IDs/choices still match. Never blindly replay, and never edit `.evospec`.

Context can include bounded, structural `external_sdd_evidence` with total and completeness metadata for recognized foreign layouts. It is content-free observation, not EvoSpec authority or a lifecycle signal. The model alone assesses whether foreign material is ACTIVE, HISTORICAL, or UNKNOWN and whether it conflicts with the requested work. Detect, understand, and preserve foreign documents; they remain observed, not EvoSpec-owned. Use the evidence only as an advisory contextual warning where relevant. Never automatically replace, migrate, integrate, rewrite, remove, disable, or select a foreign SDD process or artifact.

For a **clear low-risk request for a new single-file web app** in a fresh initialized E1 repository, use `evospec_session_first_slice(expected_revision)` to record exactly the most recent admitted user request. The tool retrieves the session message itself from OpenCode (no model-provided message ID, prompt text, Feature title or Slice title), binds it to the executing session/root/Core revision, and calls OpenCode `permission.assert` for the specific `evospec_session_intake` action. In Auto, an allowed operation normally needs no prompt; in prompt/deny mode the host's permission policy remains authoritative. The session-request route accepts paragraphs, bullet lists, tabs and CRLF, including trailing line breaks; the original host message and digest must remain byte-for-byte identical through admission. Only user-visible titles strip outside whitespace. Never ask someone to rewrite a valid prompt into one line. NUL/other unsupported controls, attachments, blank-only text or requests beyond 2048 characters remain invalid.

Core stores `source=SESSION_REQUEST` and a message digest, **not a human-authenticated TTY signature**; the Feature/Slice titles are the user's exact request, Task/checkpoint are fixed, and only a new `index.html` receives reversible bounded Core edit scope (8 operations). Host edits still require OpenCode permission. Never claim that a role `user` proves human presence; `session.prompt` may be programmatic. If the session message, root, revision, project emptiness or host permission cannot be checked, report the blocker and do not fabricate an agreement or silently enter a legacy workflow. Session intake alone does not register formal Slice criteria, certify per-criterion tests, accept a Slice outcome, or complete a Feature. The separate bounded request-scoped objective lane may emit formal verification and Slice-outcome receipts only for Core's exact supported static-page scope, never broader Feature requirements.

For other new material Features that cannot use this strictly bounded lane, `evospec_first_slice_handoff` remains an **explicit legacy interactive terminal** option with its historical TTY gate. It is not the default Auto-first experience; do not ask the user to type `ACEPTO` just because a session request is clear and eligible.

If the explicit NEW request is made while Core is `UNINITIALIZED`, `evospec_start(new)` may initialize the **executing project only**; for an empty E1 ledger it returns `SESSION_FIRST_SLICE_AVAILABLE` without materializing a legacy Feature. If Core reports a nonempty ledger, pending intake, stale revision, unavailable E1 schema or an active Feature, stop or follow the exact canonical recovery: first-Slice acceptance cannot be retrofitted or invented. For an existing lightweight correction or separately requested legacy workflow, keep the supported `evospec_start(change)` or explicit `intake_route: "legacy"` behavior. An explicit task for the executing session repository may initialize it only when current Core context legally permits `init`; do not initialize unrelated repositories. On success, use the returned fresh canonical context. If natural intake returns `DISCOVERY_LIMIT` and attributable repository evidence supports a typed assessment, use `evospec_assessed_start` with real repository-relative evidence, the correct `NEW`/`CHANGE` operation, honest confidence, existing protocol depth vocabulary, and all material ambiguities preserved. Do not invent evidence or an established Core capability ID; Core validates and may reject the assessment. Do not ask for raw JSON, a narrower root, or ordinary operational approval.

Apply the deterministic continuation directive to every current context: `SAFE_AUTOMATIC_OPERATION` means continue; `BOUNDED_DELEGATION` means continue only after Core authorizes the exact operation within the active envelope; `EXTERNAL_WAIT` means wait/poll and reevaluate; `HUMAN_MATERIAL_DECISION` means ask exactly the one decision and choices Core exposes; `STRUCTURAL_DEFECT` means fail closed unless Core offers one exact safe recovery. A terminal context with `outcome: null` completes successfully without another mutation. Do not ask whether to inspect files, run tests/builds/typechecks, delegate, refresh context, wait, retry, or continue normal lifecycle work.

Use `evospec_wait` for one bounded external wait when Core returns `EXTERNAL_WAIT`; it returns fresh context and distinguishes pending from reevaluation. Use `evospec_retry` only for recognized transient infrastructure failures, and only within Core's `retry_budget` and operation authority. Deterministic test assertions, compile/type errors, invalid schemas, missing authorization, and explicit Core rejection are not transient. Respect cancellation during every wait or retry. A pending CI/build/worker result is never success; resume the parent workflow after polling, including after delegated-worker recovery.

For an active **TTY-accepted E1 Slice outside the initial SESSION_REQUEST single-file scope** that needs to edit a file, first inspect the current `autonomy_envelope` and use Core's read-only `autonomy_evaluate` for the exact relative file and `edit` action. If a grant is missing, prefer the dedicated `evospec_propose_file_edit` helper with `expected_revision` and **only** the needed user-file path (e.g. `index.html`). It deterministically retains existing actions/paths, proposes `edit` and a **finite proportional budget** (default three remaining Core operations), and passes the exact proposal through Core. Never propose a path/action-only expansion retaining `operation_budget=0`: Core requires a finite positive budget for new grants. Do not invent a second first-Slice acceptance, use chat consent as permission, change `.evospec`, or bypass an error. On success, show the **entire** Core delta and ask only its exact `AUTHORIZE`, `REJECT`, or `NARROW` decision; the proposal by itself grants nothing. On a rejection, report the returned Core reason without blindly retrying or widening scope. After explicit authorization, reread context and independently respect OpenCode's file permissions. This helper does not run `edit`, approve Slice outcomes, or publish.
 
For **R2-C1 OpenCode Auto-first host qualification only**, call `evospec_auto_readiness` to inspect the executing session's root and the availability of host observation APIs **without changing permissions, Core state, or message history**. It can report prompt-admission events and rule effects such as `allow`, but these are **not** proof that a human submitted that prompt or that the user enabled Auto: programmatic prompts and saved permission rules also exist. Never treat `allow` or this probe as a `UserAcceptance` receipt, human identity, file-write authorization, Slice acceptance, or Feature completion. The tool deliberately returns `AUTO_HOST_ATTESTATION_UNAVAILABLE` until an attributable source is qualified in a later R2-C increment. Do not ask the user to repeat TTY approvals merely to run this read-only probe; do not claim that C1 has implemented seamless Auto-first workflows. Normal EvoSpec lifecycle gates remain unchanged.

For **R2-C2 contract qualification only**, the read-only `evospec_auto_contract` helper compares the host's exposed permission/intent signals against the **necessary** delegated-authority guarantees. It may observe a proposed upstream `permission.evaluate.rule.source` field or `permission.saved.list` API; these are **capability candidates, not signatures or approvals**. Never call saved-permission APIs from the probe, accept draft prompt metadata as a human origin, or interpret `autoaccept`, `allow`, `ask`, a `user` role, or a new event property as a delegated Core grant. Report `AUTO_DELEGATION_CONTRACT_BLOCKED` until host-origin, mode/rule source, revocation/policy epoch, and single-use execution admission are qualified. No TTY tokens, file grants, schema upgrades, auto-acceptance, feature close, or Git operations may follow from a diagnostic. This remains a developer qualification surface, **not** a required command for normal users.

An autonomy-envelope expansion is a two-step, user-controlled decision. `propose_autonomy_expansion` records only the exact requested delta and returns a proposal ID; it does not change authority. Present the proposal and Core's `AUTHORIZE`, `REJECT`, and `NARROW` choices to the user. Resolve only the exact pending proposal at the current revision. `AUTHORIZE` accepts its full recorded delta, `REJECT` preserves the prior envelope, and `NARROW` must provide a strict subset of the recorded proposal. Never create or resolve an expansion autonomously, reuse a stale proposal, or grant force pushes, history rewrites, destructive resets, tags, or releases through an envelope.

If `pending_discovery_recovery` contains exactly one complete Core-offered candidate and `recover_discovery` is currently legal, forward that exact tuple; never synthesize, omit, or replace evidence. If `pending_capability_selection` is present, the canonical outcome must supply the material decision; ask for exactly one offered choice and forward its exact `selection_id` and choice. Never auto-select an ambiguous queue candidate. For natural requests such as "show my work list", "what is blocked", "what should I do next", or "resume work X", use `evospec_work_list`, `evospec_work_next`, `evospec_work_activate`, `evospec_work_state`, or `evospec_work_relation` with the current revision and stable work IDs. Prefer `evospec_progress`, `evospec_review`, `evospec_verify`, `evospec_continue`, `evospec_clarify`, and `evospec_converge` for their matching context-authorized actions. Submit lock assessments before review when locks are active; use the raw `evospec` tool for `assess_locks` because it has no typed helper. A bounded, explicit request for review only is a stop-before-convergence boundary; do not treat it as convergence consent. `converge` is separate and needs explicit caller-authored Product Truth content when truth changes.

Treat `legal_actions` as lifecycle eligibility, not consent and not proof that every Core gate passes. Preserve earlier attributable, explicit user authorization to converge or complete only for the same repository and the same active Feature or Change, with reliable user provenance. Carry it through intermediate lifecycle actions and context recovery. Stop carrying it when the work is fulfilled, the authorization is revoked or narrowed, the active work mismatches, provenance is unreliable, or state is uncertain. It never authorizes commits, tags, or releases, and Core does not persist it. Use only the current revision's legal actions and include that exact revision in every mutation.

`AUTOMATIC` means continue the returned supported workflow autonomously. `USER` is not itself permission to invent a question: return control only for a canonical `HUMAN_MATERIAL_DECISION` with its exact decision surface. `NONE` means fail closed and report the structural defect, without a fake yes/no prompt. When lifecycle includes `IMPLEMENT`, perform the requested repository work, tests, builds, and typechecks under the user's task authority and active envelope, checkpoint meaningful progress with `evospec_progress`, then review, verify, and converge only when current context authorizes each step. Keep reloading and reevaluating until terminal completion, one material decision, an unrecoverable structural defect, or cancellation.

For a blocked or error state, use the complete latest envelope, whether returned as `result`, `context`, or `error`. Follow the current continuation directive and a supported Core recovery. Terminal `NO_ACTION` means no protocol mutation is needed. `INIT_REQUIRED` may be handled only by the explicit-task/session-root initialization rule above. Do not invent a phase transition, authorization, material choice, or remediation.

Use `context` for canonical recovery data. The read-only `status` and `doctor` surfaces are concise local dashboards and diagnostics; they do not change lifecycle state, repair files, or choose actions automatically. Read their output, then return to `context` and follow its current guidance before any mutation.

`reject` is a provider-neutral protocol action, not a standalone CLI command or native command. Send only when the latest context includes `reject` in `legal_actions`, with the exact revision: `{"action":"reject","expected_revision":N}`. Rejection terminalizes the active work using Core's existing semantics; when the active work is side work, it restores the preserved primary through Core. It remains non-converging and non-publishing.

## Bounded request-scoped static page

Treat a non-null `request_scoped_objective` from `SESSION_REQUEST` as a dedicated one-shot branch. Do not advance it with `evospec_continue`, `evospec_progress`, `evospec_review`, `evospec_verify`, `evospec_converge`, or legacy lifecycle mutations; this route may intentionally remain in `Phase.RESEARCH`, and Core owns its exact supported receipts.

If the objective is `BLOCKED`, do not call `evospec_request_scoped_objective`. There is one narrow artifact-creation case: only when canonical context binds a `source_reference` and `request_sha256` to the executing repository/session, Core supplies a valid, non-empty `heading`, `index.html` is absent, there is no unresolved material decision, and `blockers` contains exactly `REQUEST_OBJECTIVE_ARTIFACT_MISSING` and `REQUEST_OBJECTIVE_ARTIFACT_HASH_UNAVAILABLE` (order irrelevant, no other or duplicate blockers), create only the already-authorized `index.html` using normal OpenCode edit/write permission. Use the Core heading verbatim after escaping it as HTML text (`&` to `&amp;`, `<` to `&lt;`, `>` to `&gt;`, escaping ampersands first) in this inert template:

```html
<!doctype html><html><head><meta charset="utf-8"></head><body><h1>ESCAPED_HEADING</h1></body></html>
```

Add no other elements, attributes, scripts, styles, or files. This is only the current Core-authorized `index.html` creation, not a permission expansion. For incorrect or stale existing content, repair that file to the same inert template only if the current Core scope explicitly permits the exact edit and normal host permission allows it; an earlier grant is not new approval. Otherwise stop at Core's blocker. After the missing-artifact edit, reread `evospec_context`; proceed only if the same objective/source is now `PENDING`. Any other blocker or status stops this branch.

When the objective is `PENDING`, the file is ready under current scope, and there is no unresolved material decision, call `evospec_request_scoped_objective` with only `expected_revision`. Reread context after the mutation. Only when the fresh objective is `VERIFIED` for the same source and repository, with no unresolved material decision, call the tool again at that new revision to close; reread context again and stop at `COMPLETE`. The tool accepts no model-supplied heading, criterion, condition, result, stage, fingerprint, or request text.

The adapter requires the exact admitted session request that Core bound to the objective. It may recover that source across only trailing same-session user messages whose trimmed text is exactly `continue` or `continúa`, with no attachments or synthetic events; substantive new prompts, malformed resumes, or a lost original source fail closed and are never skipped. Generic requests, insufficient proof, stale scope, untrusted provenance, or any other `BLOCKED` case stop with the exact Core blocker. OpenCode's native permission policy governs each operation: do not force an ask, claim a permission dialog was shown, or describe permission admission as human approval.
