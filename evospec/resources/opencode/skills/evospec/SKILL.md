# EvoSpec Protocol

Call `evospec_context` and `evospec_continuation` before repository inspection, tests, implementation state, or EvoSpec lifecycle mutation. Internal task, todo, and reasoning work may precede context only when it does not mutate the repository or EvoSpec and does not claim authorization. Treat returned `legal_actions`, preflight requirements, lifecycle, lock metadata, outcome, Autonomy Envelope, and revision as authority. Context chooses legality; never infer an allowed action from a phase name. Every mutation includes that exact `expected_revision`; reload canonical context after every Core mutation. On `STALE_REVISION`, discard conclusions tied to the old revision, refresh, and reevaluate the intended operation; replay only when current Core legality and the exact offered IDs/choices still match. Never blindly replay, and never edit `.evospec`.

Context can include bounded, structural `external_sdd_evidence` with total and completeness metadata for recognized foreign layouts. It is content-free observation, not EvoSpec authority or a lifecycle signal. The model alone assesses whether foreign material is ACTIVE, HISTORICAL, or UNKNOWN and whether it conflicts with the requested work. Detect, understand, and preserve foreign documents; they remain observed, not EvoSpec-owned. Use the evidence only as an advisory contextual warning where relevant. Never automatically replace, migrate, integrate, rewrite, remove, disable, or select a foreign SDD process or artifact.

When current context permits intake, use `evospec_start` with `operation: "new"` or `operation: "change"` and the natural-language `intent`. An explicit task for the executing session repository may initialize it only when current Core context legally permits `init`; do not initialize unrelated repositories. On success, use the returned fresh canonical context. If natural intake returns `DISCOVERY_LIMIT` and attributable repository evidence supports a typed assessment, use `evospec_assessed_start` with real repository-relative evidence, the correct `NEW`/`CHANGE` operation, honest confidence, existing protocol depth vocabulary, and all material ambiguities preserved. Do not invent evidence or an established Core capability ID; Core validates and may reject the assessment. Do not ask for raw JSON, a narrower root, or ordinary operational approval.

Apply the deterministic continuation directive to every current context: `SAFE_AUTOMATIC_OPERATION` means continue; `BOUNDED_DELEGATION` means continue only after Core authorizes the exact operation within the active envelope; `EXTERNAL_WAIT` means wait/poll and reevaluate; `HUMAN_MATERIAL_DECISION` means ask exactly the one decision and choices Core exposes; `STRUCTURAL_DEFECT` means fail closed unless Core offers one exact safe recovery. A terminal context with `outcome: null` completes successfully without another mutation. Do not ask whether to inspect files, run tests/builds/typechecks, delegate, refresh context, wait, retry, or continue normal lifecycle work.

Use `evospec_wait` for one bounded external wait when Core returns `EXTERNAL_WAIT`; it returns fresh context and distinguishes pending from reevaluation. Use `evospec_retry` only for recognized transient infrastructure failures, and only within Core's `retry_budget` and operation authority. Deterministic test assertions, compile/type errors, invalid schemas, missing authorization, and explicit Core rejection are not transient. Respect cancellation during every wait or retry. A pending CI/build/worker result is never success; resume the parent workflow after polling, including after delegated-worker recovery.

An autonomy-envelope expansion is a two-step, user-controlled decision. `propose_autonomy_expansion` records only the exact requested delta and returns a proposal ID; it does not change authority. Present the proposal and Core's `AUTHORIZE`, `REJECT`, and `NARROW` choices to the user. Resolve only the exact pending proposal at the current revision. `AUTHORIZE` accepts its full recorded delta, `REJECT` preserves the prior envelope, and `NARROW` must provide a strict subset of the recorded proposal. Never create or resolve an expansion autonomously, reuse a stale proposal, or grant force pushes, history rewrites, destructive resets, tags, or releases through an envelope.

If `pending_discovery_recovery` contains exactly one complete Core-offered candidate and `recover_discovery` is currently legal, forward that exact tuple; never synthesize, omit, or replace evidence. If `pending_capability_selection` is present, the canonical outcome must supply the material decision; ask for exactly one offered choice and forward its exact `selection_id` and choice. Never auto-select an ambiguous queue candidate. For natural requests such as "show my work list", "what is blocked", "what should I do next", or "resume work X", use `evospec_work_list`, `evospec_work_next`, `evospec_work_activate`, `evospec_work_state`, or `evospec_work_relation` with the current revision and stable work IDs. Prefer `evospec_progress`, `evospec_review`, `evospec_verify`, `evospec_continue`, `evospec_clarify`, and `evospec_converge` for their matching context-authorized actions. Submit lock assessments before review when locks are active; use the raw `evospec` tool for `assess_locks` because it has no typed helper. A bounded, explicit request for review only is a stop-before-convergence boundary; do not treat it as convergence consent. `converge` is separate and needs explicit caller-authored Product Truth content when truth changes.

Treat `legal_actions` as lifecycle eligibility, not consent and not proof that every Core gate passes. Preserve earlier attributable, explicit user authorization to converge or complete only for the same repository and the same active Feature or Change, with reliable user provenance. Carry it through intermediate lifecycle actions and context recovery. Stop carrying it when the work is fulfilled, the authorization is revoked or narrowed, the active work mismatches, provenance is unreliable, or state is uncertain. It never authorizes commits, tags, or releases, and Core does not persist it. Use only the current revision's legal actions and include that exact revision in every mutation.

`AUTOMATIC` means continue the returned supported workflow autonomously. `USER` is not itself permission to invent a question: return control only for a canonical `HUMAN_MATERIAL_DECISION` with its exact decision surface. `NONE` means fail closed and report the structural defect, without a fake yes/no prompt. When lifecycle includes `IMPLEMENT`, perform the requested repository work, tests, builds, and typechecks under the user's task authority and active envelope, checkpoint meaningful progress with `evospec_progress`, then review, verify, and converge only when current context authorizes each step. Keep reloading and reevaluating until terminal completion, one material decision, an unrecoverable structural defect, or cancellation.

For a blocked or error state, use the complete latest envelope, whether returned as `result`, `context`, or `error`. Follow the current continuation directive and a supported Core recovery. Terminal `NO_ACTION` means no protocol mutation is needed. `INIT_REQUIRED` may be handled only by the explicit-task/session-root initialization rule above. Do not invent a phase transition, authorization, material choice, or remediation.

Use `context` for canonical recovery data. The read-only `status` and `doctor` surfaces are concise local dashboards and diagnostics; they do not change lifecycle state, repair files, or choose actions automatically. Read their output, then return to `context` and follow its current guidance before any mutation.

`reject` is a provider-neutral protocol action, not a standalone CLI command or native command. Send only when the latest context includes `reject` in `legal_actions`, with the exact revision: `{"action":"reject","expected_revision":N}`. Rejection terminalizes the active work using Core's existing semantics; when the active work is side work, it restores the preserved primary through Core. It remains non-converging and non-publishing.
