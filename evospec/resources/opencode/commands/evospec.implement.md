Read canonical continuity status and the Feature's Tasks. For explicit `--all`, first make one revision-bound `implement` call with `phase: "start"`, the exact `feature_id`, `mode: "ALL"`, and `close_feature: false` (the default); Core returns the stable mandate ID and binds the Feature's normative Outcome, criterion definitions, and Increment IDs plus normative Outcomes. There is one current mandate per Feature; selection does not redirect another Feature's mandate. Then query the queue and carry that exact Feature ID and its `mandate_id` through every `queue`, `begin`, `report`, `verify`, scoped Task addition, and detour/recovery call. One unresolved Task checkpoint remains global: it blocks a second Task start or semantic document reconciliation across all Features. Before each effect, persist `begin`; perform only the scoped work under ordinary host permissions; report the observed result afterward; verify criteria separately with the current linked Task; and re-query Core before continuing. Continue only through covered Increments in order. If an agreed Increment has no Task yet, add its Task with `tasks` and the same mandate ID; do not restart the mandate. A technical plan refinement may name an already-bound stable Increment ID and guide its Task without changing normative scope. Display-title, notes, formatting, and plan-only changes do not stale a mandate; a changed Feature Outcome, criterion definition, or Increment Outcome does, even if IDs stay the same. Reconcile first, then replace by naming that Feature's exact stale mandate ID; prior attempt/check history remains. A legacy mandate without a normative Outcome binding is stale for new effects; recover only its exact checkpoint with exact Feature, mandate, Task, session/evidence, then replace it before new effects. Never bypass an active mandate with an unbound call. There is no three-Task cap. Split/add only technically necessary Tasks within the bound scope and preserve stable IDs, dependencies, reasons, and evidence. Blocked/canceled Tasks are not successful; reopening keeps the same ID and requires a new checkpointed attempt and fresh linked check. Never blindly repeat an unresolved attempt: a different session must inspect status and reconcile the exact Task with evidence before any retry. For a newly requested related change between Tasks, persist a `RELATED` pause before its effects with the exact next Task as return; reconcile any unresolved attempt first, do not begin main work while paused, record the observed detour result, resume with the same mandate, and refresh affected checks. Do not silently add the detour to accepted Feature scope. Stop on a material decision, host denial/cancellation, failure, unknown outcome, stale scope, or no eligible work. `--all` never closes a Feature; only an explicit close request may set `close_feature: true`, and `/evospec.close` remains a separate explicit operation after Core's checks pass. `close_feature` records intent only: with `false`, wait for a later explicit close request; with `true`, carry the clear request forward without asking again. Neither setting accepts or closes the Feature. Once current evidence is grounded, record `accept` with the user's reasoned decision, then `close` using Core's exact current `acceptance_id`; do not repeat a stale request.
