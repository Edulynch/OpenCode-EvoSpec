Read canonical continuity status and the Feature's Tasks. For explicit `--all`, first make one revision-bound `implement` call with `phase: "start"`, the exact `feature_id`, `mode: "ALL"`, and `close_feature: false` (the default); Core returns the stable mandate ID and snapshots every currently accepted criterion and Increment ID/digest. Then query the queue and carry that exact `mandate_id` and Feature ID through every `queue`, `begin`, `report`, `verify`, scoped Task addition, and detour/recovery call. Before each effect, persist `begin`; perform only the scoped work under ordinary host permissions; report the observed result afterward; verify criteria separately with the current linked Task; and re-query Core before continuing. Continue only through covered Increments in order. If an agreed Increment has no Task yet, add its Task with `tasks` and the same mandate ID; do not restart the mandate. A reconciled criterion/Increment scope change makes the old mandate stale; explicitly reconcile, then start a replacement naming that exact stale mandate ID. Never bypass an active mandate with an unbound call. There is no three-Task cap. Split/add only technically necessary Tasks within the bound scope and preserve stable IDs, dependencies, reasons, and evidence. Blocked/canceled Tasks are not successful; reopening keeps the same ID and requires a new checkpointed attempt and fresh linked check. Never blindly repeat an unresolved attempt: a different session must inspect status and reconcile the exact Task with evidence before any retry. For a newly requested related change between Tasks, persist a `RELATED` pause before its effects with the exact next Task as return; reconcile any unresolved attempt first, do not begin main work while paused, record the observed detour result, resume with the same mandate, and refresh affected checks. Do not silently add the detour to accepted Feature scope. Stop on a material decision, host denial/cancellation, failure, unknown outcome, stale scope, or no eligible work. `--all` never closes a Feature; only an explicit close request may set `close_feature: true`, and `/evospec.close` remains a separate explicit operation after Core's checks pass. A checkpoint is durable bookkeeping, not a filesystem grant, evidence of success, or permission approval. User input: $ARGUMENTS
